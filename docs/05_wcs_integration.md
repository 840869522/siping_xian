# 模块五：任务调度与WCS集成模块

## 模块概述

该模块是实现仓库自动化的核心，是连接上层WMS业务逻辑与下层物理自动化设备的“神经中枢”。其设计展现了高度的模块化、灵活性和健壮性，能够与来自不同供应商的多种WCS（仓库控制系统）和硬件进行集成。

主要职责包括：
1.  **自动化任务调度**: 通过一系列后台守护线程，持续不断地轮询WMS内部生成的业务任务（如拣货、上架、移库等）。
2.  **协议适配与翻译**: 将WMS内部标准的任务格式，**翻译**成特定WCS供应商所需的、截然不同的API请求格式和协议。这是该模块的核心价值所在，完美体现了**适配器（Adapter）设计模式**。
3.  **流量控制与缓冲**: 在向WCS下发任务前，会检查当前已下发但未完成的任务数量，如果超过预设阈值，则暂停下发。这是一个重要的缓冲机制，防止因WMS下发过快而导致物理设备拥堵或WCS系统过载。
4.  **双向通信架构**: 不仅支持WMS向WCS下发指令，还通过提供回调API接口，支持WCS在发生特定事件时主动通知WMS，构成了完整的、事件驱动的闭环通信。

## 文件深度分析

### 1. `wcs/` 目录下的线程类 (`ThreadB`, `ThreadD`, `ThreadP`)

*   **文件职责**: 这一系列`Thread`类是WCS集成的核心执行单元。每一个线程都是一个针对特定库区或特定WCS供应商的**“适配器”**。
    *   `ThreadB`: 负责**B库（料箱库）**，对接“Z”公司的WCS，控制**穿梭车**。
    *   `ThreadD`: 负责**D库（大件库）**，对接“速锐”公司的WCS。
    *   `ThreadP`: 负责**P库（托盘库）**，同样对接“Z”公司的WCS，控制**堆垛机**。

*   **关键方法分析 (`run()`方法)**: 所有线程都遵循一个统一、健壮的**“查询-翻译-下发-更新”**调度循环模式。
    1.  **查询**: `taskBService.list(wrapper)` 从各自的任务表（`t_task_b`, `t_task_d`, `t_task_p`）中查询出`status = '待执行'`的任务。
    2.  **流量控制**: 查询`status = '已下发'`的任务数，若超过预设阈值（例如B库为30，D库为5），则`continue`跳过本次循环，等待下次唤醒，以此实现流量控制。
    3.  **任务翻译 (适配器核心)**: 这是最关键的步骤。根据任务类型，将WMS的`Task`对象字段，逐一映射到WCS特定API要求的`ZTask`或`DtaskReceive`对象字段中。
        *   **协议转换**: 将WMS的业务术语（如“出库”）转换为WCS的技术指令（如`mfc_out_task`字符串或整数`1`）。
        *   **数据格式化**: 对货位号等数据进行解析和格式化（例如，将WMS的`AA010203`转换为WCS需要的`1_2_3`坐标格式）。
    4.  **HTTP下发**: 使用`RestTemplate`将翻译好的任务对象通过HTTP POST请求发送到在配置文件中指定的、对应WCS的API地址。
    5.  **状态更新**: 根据WCS返回的HTTP响应，将WMS中的任务状态原子性地更新为“已下发”或“下发出错:[具体错误信息]”，为后续的监控和排错提供了依据。

### 2. `wcs/ThreadSort.java`

*   **文件职责**: 自动化分拣机（Sorter）的专属任务调度器。
*   **实现模式**: 采用了一种更高级的**“查询-触发”**模式。
    *   **查询**: 轮询`t_task_sort`表，查找待执行的波次分拣任务（`wave_sort_task`）。
    *   **触发**: 它不直接构造HTTP请求与WCS通信，而是通过`SpringUtil.getBean()`获取`TaskZController`的实例，并直接**调用其内部的`ZDKtaskSorter`方法**。
*   **设计解读**: 这种设计表明，启动一个分拣任务可能需要大量复杂的前置准备工作（如订单汇总、格口计算等）。设计者将这些复杂逻辑与WCS通信细节一起封装在了`TaskZController`的方法中，使得`ThreadSort`的职责被简化为纯粹的“调度器”，而`TaskZController`则成为一个可被多方（后台线程、前端页面）复用的、高级的业务服务。

### 3. `wcs/ThreadX.java`

*   **文件职责**: 一个**开发模板或占位符**。
*   **实现分析**: 其内部的核心逻辑均被注释，日志输出也忘了修改。
*   **设计解读**: 它的存在表明团队在进行WCS集成时，遵循一种标准化的、可复用的开发模式。当需要集成新设备时，开发者可以复制此类，并在预留的框架内填充具体的任务查询、翻译和下发逻辑。

### 4. `controller/WCSController.java`

*   **文件职责**: 为外部WCS系统提供**回调（Callback）API接口**，实现**WCS -> WMS**的反向通信。
*   **实现分析**:
    *   提供了`/api/ReceWms/CreateOutTask`和`/api/ReceWms/CreateMoveTask`等接口。
    *   当前这些接口的实现仅为**存根（Stub）**，它们只记录收到的请求日志，并立即返回一个硬编码的成功响应，尚未实现任何实际的业务逻辑。
*   **设计解读**: 这个控制器的存在，表明系统在架构设计上考虑了完整的、双向的、事件驱动的集成模型。它为未来实现由设备事件触发的自动化流程（如未知托盘到达入口，WCS通知WMS为其创建入库任务）预留了清晰的扩展点。

### 5. 任务实体 (`entity/task/`)

*   **文件职责**: `TaskB`, `TaskD`, `TaskP`, `TaskSort`等实体类，分别定义了WMS为不同库区或设备生成的内部标准任务的数据结构。
*   **关键字段**:
    *   `task_no`: 唯一的任务编号。
    *   `task_type`: 任务类型（出库、入库、移库等）。
    *   `pallet_code`: 操作的载具条码。
    *   `location_code`: 目标货位。
    *   `prot_no`: 目标端口/工作站。
    *   `status`: 任务的生命周期状态（待执行、已下发、已完成、下发出错等）。
    *   `udf...`: 备用字段，常用于在复杂业务（如移库）中传递额外信息（如源货位）。
